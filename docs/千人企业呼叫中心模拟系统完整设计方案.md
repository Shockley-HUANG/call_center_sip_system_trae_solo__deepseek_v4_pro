## 一、项目整体概述

### 1.1 项目定位

本项目为**1000人规模中型企业**模拟呼叫中心系统，完全贴合真实商用通信架构，适配后续基于 **C/C++ + Lua + SIP + FreeSWITCH** 开发练习。系统支持外部400总机呼入、内部全员分机互通、部门专属路由、24小时人工客服，覆盖企业日常通话、客服接待、内部通信全场景。

### 1.2 核心业务目标

- 内部：1000名员工独立分机、各部门专属短号，支持内部免费互拨、转接、呼叫保留
- 外部：统一400官方总机入口，外部客户可自助导航对接各业务部门
- 客服：独立24小时人工服务台，承接全渠道咨询、售后、投诉工单
- 技术：实现**C底层通信调度 + Lua业务路由配置**的行业标准架构，可用于编码实战、AI Coding练习

### 1.3 系统核心特性

- 分级路由：总机IVR导航 → 部门队列 → 人工坐席兜底
- 7×24小时值守：人工客服轮班+夜间智能语音值守
- 内外分离：内部短号互通、外部400公网接入，权限隔离
- 动态配置：所有路由规则、部门配置、时间策略由Lua脚本热更新，无需重启C服务
- 高并发支撑：适配千人企业并发通话、多路呼叫同时调度

### 6.3 底层核心技术全套详解（呼叫中心专用）

本节逐一对呼叫中心五大底层核心技术做**通俗、业务化、可落地**解析。

#### 6.3.1 C/C++（通信服务底层核心语言）

**核心定位：呼叫中心的「底层引擎骨架」**

所有通信服务、高并发调度、网络收发、内存管理核心逻辑，全部由 C/C++ 实现，是整个系统的性能底座。

**在本项目中的核心作用**：
- 负责**底层网络IO、并发调度、信令与媒体数据收发**
- 管理通话会话生命周期：创建、接通、保持、转接、挂断、资源释放
- 极致低延迟、高吞吐，支撑千人企业多路并发通话不卡顿
- 提供 C 接口，对接 Lua 脚本，实现「底层硬逻辑 + 上层软配置」分层架构

**为什么不用 Python/Java**：呼叫中心属于实时硬实时业务，Java/Python 有GC卡顿、线程开销大、延迟高，无法支撑语音实时传输，C/C++ 无虚拟机、内存可控、内核交互直接，是通信行业唯一首选。

#### 6.3.2 Linux Socket（网络通信入口）

**核心定位：通话数据的「传输通道」**

Socket 是 Linux 系统提供的网络编程接口，所有网络程序的收发数据，都必须通过 Socket，是SIP、RTP通信的基础载体。

**呼叫中心用到的两类Socket**：
- **UDP Socket（主力）**：SIP信令、RTP语音媒体流，无连接、开销小、延迟极低，适合实时通话场景
- **TCP Socket（辅助）**：话单上报、日志同步、后台管理指令，保证数据可靠不丢失

**通俗理解**：Socket就是水管，SIP/RTP是水管里的水流，没有Socket，所有通话数据无法传输。

#### 6.3.3 epoll（Linux高并发IO多路复用核心）

**核心定位：呼叫中心的「并发调度中枢」**，支撑万人级并发通话的关键技术

epoll 是 Linux 内核提供的**事件驱动IO多路复用机制**，替代传统 select/poll，专门解决海量连接高并发场景的CPU浪费问题。

**核心工作原理（极简通俗）**：
- 内核维护**红黑树**：存储所有需要监听的Socket文件描述符（FD），增删改查效率O(logN)
- 内核维护**就绪链表**：只存放「有数据、有事件」的活跃连接
- 程序只需遍历就绪链表，无需轮询所有连接，CPU开销极低，并发性能趋近O(1)

**三大核心系统调用**：
1. `epoll_create()`：创建epoll调度实例
2. `epoll_ctl()`：添加/删除/修改监听的Socket事件
3. `epoll_wait()`：阻塞等待就绪事件，批量处理活跃通话请求

**通俗对比**：select是挨个点名查所有人，epoll是只叫醒有事的人，超高并发下性能碾压传统IO模型

#### 6.3.4 SIP 协议（呼叫信令控制协议）

**核心定位：通话的「指挥调度员」**，只管「控制流程」，不管语音数据

SIP（Session Initiation Protocol，会话初始协议）是VoIP呼叫中心的标准应用层协议，遵循RFC3261标准。

**本项目SIP完整工作链路**：
客户拨打400 → SIP INVITE请求上报服务器 → C底层接收请求 → 调用Lua路由脚本判断转接目标 → SIP下发振铃/接听指令 → 打通通话链路

**重点区分**：SIP只传「控制指令」（文字信令），**不传语音声音**，语音由RTP负责。

#### 6.3.5 RTP 协议（实时语音传输协议）

**核心定位：通话的「声音运输车」**，只管「传语音数据」，不管流程控制

RTP（Real-time Transport Protocol）实时传输协议，专门负责**实时传输语音、视频媒体流**，运行在UDP之上。

**RTP核心特性**：
- 低延迟：基于UDP，无握手重传，优先保证实时性
- 时序纠错：自带时间戳、序列号，防止语音乱序、卡顿、杂音
- 适配编解码：支持G.711、OPUS等电话通用编码格式

**SIP与RTP黄金分工**：
- **SIP**：信令层 → 管「怎么打通、怎么转接、怎么挂断」（控制流程）
- **RTP**：媒体层 → 管「双方说话声音实时传输」（真实数据）

#### 6.3.6 整套底层技术联动闭环（完整通话链路）

一次完整的400进线通话，底层技术完整执行顺序：

1. **C程序 + Linux Socket**：监听5060端口，接收用户SIP拨号请求
2. **epoll**：并发调度，不阻塞，同时处理多路来电
3. **SIP协议**：解析拨号请求、触发IVR流程、等待路由决策
4. **Lua脚本**：动态判断路由规则（部门分流、人工兜底），返回转接目标
5. **SIP协议**：下发指令，协商双方端口、编码，建立媒体通道
6. **RTP协议**：双向实时传输语音流，实现正常通话
7. 通话结束：SIP下发挂断指令，回收Socket资源、释放会话

**终极架构总结**：
C/C+++epoll 提供高性能并发底座，Socket提供网络通道，SIP负责呼叫信令控制，RTP负责语音媒体传输，Lua负责动态业务路由，构成商用呼叫中心标准技术架构，兼顾高性能与灵活可配置。

## 九、迭代2 — 全场景商用路由能力（V2.0 新增）

### 9.1 迭代概述

迭代2在 V1.0 基础路由能力之上，全面升级为**企业400呼叫中心全场景商用路由系统**，新增坐席状态管理、排队队列、时段判断、夜间兜底、无效按键容错、超时重试、留言提示等全套机制。所有业务逻辑纯Lua脚本化，支持热更新。

### 9.2 可配置参数中心（ROUTE_CONFIG）

所有路由参数集中管理，通过 `update_route_config()` 运行时热更新：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| ivr_timeout | 5秒 | IVR超时时间 |
| max_invalid_keys | 3次 | 无效按键连续错误上限 |
| max_queue_size | 10人 | 排队最大人数 |
| queue_timeout | 60秒 | 排队超时 |
| work_hours.start | 08:00 | 工作时段开始 |
| work_hours.end | 18:00 | 工作时段结束 |
| work_days | 周一至周五 | 工作日配置 |
| night_duty_dept | support | 夜间值班部门 |
| overflow_priority | [support,sales,service,market] | 溢出优先级 |

### 9.3 坐席状态管理系统

维护4种坐席状态，全部分机初始化为空闲在线：

| 状态 | 说明 |
|------|------|
| idle | 空闲，可接听 |
| talking | 通话中 |
| offline | 离线 |
| busy | 忙碌（临时不可接听） |

每个坐席记录：`{state, calls, last_active, extension, department}`

**负载均衡算法**：同部门空闲坐席按 `last_active` 升序轮询分配（最久未接听的优先）。

### 9.4 排队队列管理

- 按部门维度独立维护排队队列
- 最大排队人数可配置（默认10人）
- 排队超时自动清理（默认60秒）
- 队列满后自动转入留言提示

### 9.5 时段判断 + 夜间兜底路由

**判断逻辑**：
1. 取当前系统时间（os.date）
2. 匹配工作日配置（周一至周五）
3. 匹配工作时段（08:00-18:00）
4. 工作日+工作时 → 标准路由
5. 其余 → 夜间/休息模式

**夜间兜底链条**：
- 值班坐席有空闲 → 转接值班人工坐席（NIGHT_MODE, code=6）
- 值班坐席全忙 → 返回夜间忙线提示（NIGHT_MODE, code=6）
- 无任何值班坐席在线 → 留言提示（VOICEMAIL, code=7）

### 9.6 无效按键容错逻辑

- 累计计数：按 caller_id 维度独立计数
- 未超限（<3次）：返回 `INVALID_KEY_RETRY (code=9)`，播报重新引导语音
- 超限（≥3次）：自动转接人工坐席 `FALLBACK_AGENT (code=4)`，重置计数
- 通话结束后调用 `reset_invalid_key_count()` 清理

### 9.7 超时无操作兜底逻辑

- 首次超时（5秒无操作）：返回 `TIMEOUT_RETRY (code=8)`，播报重试引导
- 二次超时：自动转接人工坐席 `FALLBACK_AGENT (code=4)`
- 超时重试次数：2次（首次重试 + 二次转人工）

### 9.8 内部分机互呼路由增强

V2.0 在内部分机互呼中新增：
- **主叫有效性校验**：主叫分机必须属于企业号段

### 9.10 7大标准化路由接口

以下7个函数对外暴露，供 C 层通过 `lua_vm_route_dispatch()` 调用，全部返回标准 `route_response_t` 结构：

#### 接口1: get_ivr_route(phone, key_input)

IVR按键路由分发，入口函数。

**参数**：
- `phone` (string): 主叫号码
- `key_input` (string): 用户按键（"0"/"1"/"2"/"3"）

**返回值**：route_response_t

**内部链路**：空输入→超时兜底 → 无效按键→容错重试 → 部门匹配→状态检查 → 空闲坐席分配 / 全忙溢出

#### 接口2: check_agent_status(dept_id)

部门坐席状态检测。

**参数**：
- `dept_id` (string): 部门 key（如 "sales"）

**返回值**：
- code=0 (SUCCESS): 有空闲坐席，附详细统计
- code=2 (DEPT_FULL): 在线坐席全部忙碌
- code=3 (AGENT_OFFLINE): 全部离线

#### 接口3: overflow_route(dept_id, caller_id)

坐席全忙溢出路由，四级溢出策略：

1. 溢出到公共人工组（support）
2. 按优先级溢出到其他对外部门
3. 所有部门全忙 → 进入排队队列
4. 排队满 → 留言提示

**参数**：
- `dept_id` (string): 全忙部门 key
- `caller_id` (string, 可选): 主叫号码（用于排队）

#### 接口4: time_judge_route()

时段判断+夜间兜底路由，无参数。

**返回值**：
- code=0: 工作日时段
- code=6 (NIGHT_MODE): 夜间模式+值班坐席
- code=7 (VOICEMAIL): 无值班坐席留言提示

#### 接口5: invalid_key_fallback(caller_id, key_input)

无效按键容错兜底。

**参数**：
- `caller_id` (string): 主叫号码
- `key_input` (string): 无效按键值

**返回值**：
- code=9 (INVALID_KEY_RETRY): 未超限，重新引导
- code=4 (FALLBACK_AGENT): 超限，转人工

#### 接口6: timeout_fallback(caller_id)

用户超时无操作兜底。

**参数**：
- `caller_id` (string): 主叫号码

**返回值**：
- code=8 (TIMEOUT_RETRY): 首次超时，重试引导
- code=4 (FALLBACK_AGENT): 二次超时，转人工

#### 接口7: dept_internal_call_route(caller, callee)

内部分机互呼路由。

**参数**：
- `caller` (string): 主叫分机号
- `callee` (string): 被叫分机号

**返回值**：
- code=0 (SUCCESS): 路由成功，直连被叫
- code=1 (INVALID_DIGITS): 主叫或被叫无效
- code=2 (DEPT_FULL): 被叫正忙
- code=3 (AGENT_OFFLINE): 被叫离线

### 9.11 C层新增接口：lua_vm_route_dispatch

为支持迭代2新增的7个标准化路由接口，C层新增通用路由调度函数：

```c
int lua_vm_route_dispatch(lua_vm_t *vm, const char *func_name,
                          route_response_t *response,
                          const char *fmt, ...);
```

使用格式串 `'s'/'d'` 指定参数类型，内部自动完成：
1. 获取 Lua 全局函数
2. 按格式串压入参数
3. lua_pcall 保护调用
4. 从返回 table 提取 code/target/department/description
5. 清理 Lua 栈

**调用示例**：
```c
lua_vm_route_dispatch(vm, "get_ivr_route", &resp, "ss", "4001234567", "1");
lua_vm_route_dispatch(vm, "check_agent_status", &resp, "s", "sales");
lua_vm_route_dispatch(vm, "dept_internal_call_route", &resp, "ss", "2001", "1001");
```
